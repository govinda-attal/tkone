# Contract engine — Models

Status: **architecture only**, like the [contract engine](contract-engine.md)
it belongs to. The sketches show what a model author writes and sees; they
are illustrative, not APIs.

A model's data outlives its code. A thirty-year mortgage sees dozens of model
versions; an entry booked in 2026 is read in 2050; a party may ask to be
forgotten while the bank must keep their bookings. Most of what goes wrong in
a model layer, in any domain, comes from those three facts. The rules here
are the ones that are expensive to add once data exists, so a model has them
from its first version:

| # | Rule | What the author writes | Decision |
|---|---|---|---|
| 1 | [Fields have stable identities](#1-fields-have-stable-identities) | nothing; a rename is `#[renamed]`; `model.lock` is committed | C18 |
| 2 | [Models grow; they do not break](#2-models-grow-they-do-not-break) | `#[deprecated]`, a new field for a new meaning | C18 |
| 3 | [Compatibility is checked per kind](#3-compatibility-is-checked-per-kind) | nothing, by default | C18 |
| 4 | [Personal data is classified, and can be erased](#4-personal-data-is-classified-and-can-be-erased) | `#[personal]`, `subject`, `retain` | C19 |
| 5 | [Numbers are exact](#5-numbers-are-exact) | `Money`, `Rate`, `Decimal<S>`; explicit rounding | C20 |
| 6 | [Every collection is bounded](#6-every-collection-is-bounded) | `max` on relations, collections and `requires` | C21 |
| 7 | [Hot accounts are not serialised](#7-hot-accounts-are-not-serialised) | usually nothing; `#[ledger(guard)]` per definition | C22 |
| 8 | [Every record names its schema](#8-every-record-names-its-schema) | nothing | C23 |
| 9 | [Identities are typed, and survive merges](#9-identities-are-typed-and-survive-merges) | `#[identifiers]`; schemes as reference data; idempotency keys | C24 |

---

## The schema

A model crate is turned into a **schema**: the model described as data, which
`tkone model plan` and `apply` work from, and the engine is driven by (C16).

- **Canonical JSON** ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)):
  sorted keys, one number format, no insignificant whitespace, so the same
  model always has the same bytes, and so the same digest. It is readable in
  a plan's diff and by any tool in any language.
- **Published by digest** as an OCI artifact of media type
  `application/vnd.tkone.model.schema.v1+json`. The `v1` versions the schema
  format itself, separately from the models written in it.
- **No floats; large integers and decimals as strings; duplicate keys
  rejected; identifiers in ASCII.** Each removes a way for two tools to read
  the same schema differently.

A binary encoding (deterministic CBOR) of the same structures can be added if
size ever matters; the digest stays on the canonical JSON, so a schema never
has two identities.

## 1. Fields have stable identities

Every entity, field, relation and view has a numeric **id**, separate from its
name. Storage, the schema and the WIT types a component sees all refer to the
id; the name is for people. So a rename is free, and a name can never be
reused for something else by accident.

Ids are assigned by tooling, not written by hand. `tkone model export`
records them in **`model.lock`**, committed beside the crate, as `Cargo.lock`
is:

```toml
# model.lock: generated by `tkone model export`. Commit it.
[entity.Party]
id = 3
fields = { party_id = 1, kind = 2, legal_name = 4, date_of_birth = 6, tax_id = 7 }
retired = [5]     # removed before any version was published; never reused
```

A rename says what it was, so the lock keeps the id:

```rust
#[entity(key = party_id)]
struct Party {
    party_id: PartyId,
    kind: PartyKind,
    #[renamed(from = "name")]
    #[effective] legal_name: Name,
}
```

Without `#[renamed]`, export refuses to guess:

```text
error: field `Party.name` (id 4) is in model.lock but not in the model
  = help: if it was renamed, add #[renamed(from = "name")] to its new name
  = help: if it is no longer used, keep it and mark it #[deprecated]
```

Before a version is published, the lock may be edited freely. Once a version
is published, the lock is **append only**: CI runs `tkone model check`, which
compares it with the last published schema.

## 2. Models grow; they do not break

Semver alone allows a major version to remove or redefine a field. Facts are
never migrated (C13), so data written under every past version stays in the
store, and every reader must still understand it. So the default is
**growth**:

- **Add** fields, entities, relations, views, code-set values.
- **Deprecate** what is no longer wanted. A deprecated field stays readable
  for ever and writable while a `live` or `deprecated` implementation writes
  it (the registry knows which, C7, C10).
- **A new meaning is a new name.** A field is never retyped or redefined in
  place.

Changing a notice period from calendar days to a period that may be in
business days:

```rust
#[extends(core::Account, when = "product_line = 'deposits'")]
struct DepositTerms {
    #[deprecated(since = "3.2.0", use = "notice")]
    #[effective] notice_days: u16,
    /// Calendar or business days, with the calendar to count them in.
    #[effective] notice: Option<NoticePeriod>,
}
```

```text
$ tkone model plan deposits@3.2.0
deposits 3.1.0 → 3.2.0                       growth only: minor ✔
  + DepositTerms.notice        field 9   Option<NoticePeriod>
  ~ DepositTerms.notice_days   field 4   deprecated; written by 2 live implementations
  postgres  ALTER TABLE deposits_deposit_terms ADD COLUMN f9 jsonb;
  scylla    ALTER TABLE deposits_deposit_terms ADD f9 text;
  views     AccountState: no change
```

A breaking change is the exception, never the shortcut: `--allow-breaking`,
a reason, and an approval by the role that owns the model; the version must
be major. Re-keying is never a change to an entity: it is a new entity, filled
from the journals, beside the old one. Expand, then contract, as in
[applying models](contract-engine.md#applying-models), is how the old one is
retired.

## 3. Compatibility is checked per kind

Each kind of data has the compatibility it needs, and `model plan` checks it.
Authors declare nothing unless they want stricter:

| Kind | Must hold | Because |
|---|---|---|
| Facts | **every reader reads every version** (full, transitive) | never migrated; read for decades |
| Effective and fixed attributes | new readers read all old data (backward, transitive) | versions are kept; old values are read as of their time |
| Series | backward, transitive | restated, never reshaped |
| Views | **none**: a changed view is a new view version, rebuilt from the journals, then swapped | derived (C4) |
| Operation payloads | backward: callers on an older version are still accepted | callers upgrade on their own schedule |

**Each component reads the version it was built for.** An implementation
built against `deposits@3.1` is given its inputs in the 3.1 shape, by field
id, even when 3.2 is applied: a field added in 3.2 is left out; a
deprecated field is still given. So a model's minor version never breaks a
component's WIT records, and implementations move to the new shape when
their definition does (C9).

## 4. Personal data is classified, and can be erased

A journal that is never rewritten conflicts with a right to erasure. The
answer is to know, when data is written, which fields are personal and whose,
and to encrypt them so that deleting a key erases them everywhere at once:
the journal, every view, every backup.

```rust
#[entity(key = party_id, subject = party_id, retain = "after(closed) + 7y")]
struct Party {
    party_id: PartyId,
    kind: PartyKind,                                   // internal (the default)
    #[personal] #[effective] legal_name: Name,
    #[personal(special)] date_of_birth: NaiveDate,     // special category
    #[personal(search = "exact")] #[effective] email: Email,   // findable by exact value
}

#[fact(key = account_id)]
struct Entry {
    account_id: AccountId,
    address: BalanceAddress,
    amount: Money,
    side: Side,
    /// Payment references carry names. Free text is never left unclassified.
    #[personal(subject = "counterparty")] narrative: Option<Text>,
}
```

- **Classes:** `public`, `internal` (the default), `confidential`,
  `personal`, `personal(special)`. Export refuses a free-text field
  (`String`, `Text`) without an explicit class: free text is where personal
  data hides.
- **Subject:** whose data it is: a party, found by the field `subject` names.
  Each subject has a data key; personal fields are stored encrypted with it
  (envelope encryption: the data key is itself encrypted by a key service).
- **Erasure** deletes the subject's key. Their personal fields then read as
  `Erased` everywhere. Amounts, dates and account ids are not personal by
  themselves; with the party's personal fields gone they are pseudonymous,
  which is how bookings stay for the retention periods regulators require.
  Whether that suffices in a jurisdiction is a question for its lawyers, and
  the model makes the answer a configuration, not a migration.
- **Retention** (`retain`) is a policy the engine runs: when it passes, the
  subject is erased, unless a **legal hold** is on them.
- **Search** on personal data is by exact value only, through a keyed hash
  (a blind index), never by range or prefix.
- **Entitlements read the classes.** Masking, and who may read
  `personal(special)` at all, are policies over classes, not lists of
  fields ([entitlements](contract-engine.md#entitlements)).
- **Hooks see personal data only when they declare it.** A manifest's
  `requires` names each personal field it needs; anything else is withheld.
  Few hooks need a name; a sanctions check might.

A replay of an erased subject's calls cannot reproduce their personal inputs.
That is the point of erasure, and the recorded input hashes still prove what
was given at the time.

## 5. Numbers are exact

`f32` and `f64` are refused in models, definitions and the contract SDK. A
float gives two components, or a component and its replay, different cents.

| Type | Holds | Notes |
|---|---|---|
| `Money` | an amount in a currency, in minor units (`i128`) | minor units per currency are reference data: 2 for GBP, 0 for JPY, 3 for BHD |
| `Rate` | a decimal rate, scale 12 | `0.0325`, a daily rate |
| `Decimal<S>` | a fixed-point decimal of scale `S` | for anything else exact |
| `Quantity<U>` | a decimal amount of a unit | other domains: `kWh`, `GB`, `minutes` |

**Rounding is never implicit.** An operation that can produce a value finer
than its type returns `Unrounded<T>`. Only `T` can be booked, except to a
balance type the model declares with extra precision:

```rust
#[balance(scale = 12)]            // in the model: accruals are kept finer than pennies
Accrued,

// each day, in the end-of-day hook:
let daily: Unrounded<Money> = balances.available * rate.daily(DayCount::Act365Fixed);
book! { debit ("interest_accrued", daily), credit (This, Accrued, daily) };

// at capitalisation:
let interest: Money = balances.accrued.round(params.ROUNDING);   // HalfEven, by parameter
book! { debit (This, Accrued, interest), credit (This, Available, interest) };
```

The rounding mode is a parameter or a constant of the definition, so it is
versioned and visible. Accruals are kept unrounded and rounded once, when
capitalised, so a year of daily accruals does not lose a year of fractions
of a penny; what rounding leaves stays in the accrued balance for next
time.

## 6. Every collection is bounded

An unbounded read is an outage waiting for its customer: the corporate party
with 40,000 accounts, the ten-year account with a million entries. Every
collection the engine may load whole has a bound:

```rust
/// A party holds at most 50 accounts in each role, as a relation.
/// Beyond that (corporates), use the paginated view AccountsByParty.
#[relation(Account <-> Party, max_per_party = 50, max_per_account = 20)]
struct AccountPartyRole { #[effective] role: Role }

#[fact(key = booking_id)]
struct Booking { booking_id: BookingId, #[bounded(max = 1000)] entries: Vec<Entry> }
```

```yaml
requires:
  end_of_day:
    - entries: { since: last(capitalise), until: due, max: 2000 }
```

- **A `requires` without a bound is refused at registration.** Bounds come
  from the model (`max`), or from a window and an explicit `max`.
- **A call whose inputs exceed their bound is not made.** It goes to an
  operator with the reason; nothing is truncated silently.
- **To fold many rows, declare a view that folds them as they are written.**
  Accrued interest is a view, kept by the engine; a hook that re-reads a
  quarter of entries each night is a design to change.
- **Partitions are bounded too.** An instance's journal is bucketed by period
  (`(instance, month)` by default) so no partition grows for thirty years.
  This is storage; authors do not see it.

## 7. Hot accounts are not serialised

Commits are one writer per instance (C6). An account that is part of almost
every booking (fee income, suspense, a merchant receiving card settlements)
would make every commit in the bank wait for it.

The rule: **a write is serialised only if a decision reads the value it
changes.** A debit checked against a balance must be. A credit never makes a
passed check fail, and entries to accounts with no limit have no check, so
neither needs to wait: they are **delivered**. What the author writes is
usually nothing:

```rust
// Customer accounts: debits are checked against the balance, in order.
#[definition(name = "easy-saver", version = "2.0.0", model = "deposits@^3.1")]
#[ledger(guard = "debits")]               // the default; may be omitted
mod easy_saver { /* ... */ }

// Internal accounts: no check, so nothing is serialised.
#[definition(name = "fee-income", version = "1.0.0", model = "core@^1.4")]
#[ledger(guard = "none")]
mod fee_income { /* ... */ }
```

The model refuses what would break the rule: a hook may read an unguarded
account's balance only from an `eventual` view, with a stated lag, never as
a check. How delivery is stored and read, why it is safe, and what it costs:
[hot accounts](hot-accounts.md).

## 8. Every record names its schema

Each journal record carries the digests of the schemas it was written under,
and the code that wrote it:

```text
record  instance acc_01JD…  version 1842  bucket 2026-11
        schemas         core@sha256:9f1c…  deposits@sha256:41aa…
        implementation  sha256:c07e…  (easy-saver@2.0.0)
        engine          0.4.1
        inputs          sha256:5b2d…
        actions         Book { … }
```

Rows in tables carry a small schema number, resolved through a dictionary of
digests. A reader never guesses which shape it is reading: it decodes by field
id under the named schema, then **lifts** the value to the version it reads
at. Growth makes lifting mechanical: a field the old schema lacks is `None` or
its declared default. `tkone journal show acc_01JD… --as-written` shows a
record in the shape it was written in.

## 9. Identities are typed, and survive merges

An object has one **key** and a **set of identifiers**:

| | Example | Made by | Seen by |
|---|---|---|---|
| **Key** | `acc_01JD3K…` | the engine | systems only; never printed on a statement |
| **Bank-issued identifiers** | account number and sort code, IBAN, customer number, card PAN | the bank, at opening or later | customers, channels, other banks |
| **External identifiers** | passport, national id, tax id, LEI, a CRM's id, a migrated core's account number | someone else | onboarding, imports, regulators |

Which schemes an object carries depends on what it is: a UK current account
has a sort code and account number and an IBAN; a card account has a PAN; an
organisation has an LEI and a person a passport, maybe two. Banks add schemes
as they enter markets and replace systems. So **schemes are reference data**
(an open code set), not attributes in the model. The model says only that an
entity has a set:

```rust
#[entity(key = account_id)]
#[identifiers]                      // a set of (scheme, value), effective-dated
struct Account { account_id: AccountId, /* ... */ }

#[entity(key = party_id, subject = party_id)]
#[identifiers]
struct Party { party_id: PartyId, /* ... */ }
```

Each scheme says what it applies to, how its values are checked and
normalised, how unique they are, how many an object may hold, who issues
them, and whether they are personal:

```yaml
# reference/identifier-schemes.yaml: loaded with `tkone reference load`
- scheme: sort-code-account
  applies_to: Account
  format: uk-sort-code-account     # built-in: digits, modulus check
  unique: global
  per_object: one-active           # one at a time; earlier ones still resolve
  issued_by: bank                  # allocated by the engine
  reuse: never

- scheme: iban
  applies_to: Account
  format: iban                     # ISO 13616: country, check digits
  derived_from: sort-code-account  # computed when that is issued; never typed in
  unique: global
  per_object: one-active
  issued_by: bank

- scheme: pan
  applies_to: Account
  format: pan                      # Luhn
  unique: global
  per_object: many                 # reissued cards; several active during a replacement
  issued_by: bank
  stored_as: token                 # the PAN itself stays in a card vault

- scheme: passport
  applies_to: Party
  when: "kind = 'person'"
  unique: per-issuer               # (issuing country, number)
  per_object: many
  issued_by: external
  class: personal                  # encrypted per subject; exact search only

- scheme: lei
  applies_to: Party
  when: "kind = 'organisation'"
  format: lei                      # ISO 17442
  unique: global
  per_object: one
  issued_by: external

- scheme: legacy-core
  applies_to: [Account, Party]
  unique: per-system
  per_object: one
  issued_by: external
  system: core-2009                # the migrated system's own ids
```

A **definition** says which schemes its product issues and which it needs
before opening:

```rust
#[definition(name = "current-account-uk", version = "1.0.0", model = "deposits@^3.1")]
#[identifiers(issue = ["sort-code-account", "iban"])]     // iban follows, derived
mod current_account_uk { /* ... */ }

#[definition(name = "business-account", version = "1.0.0", model = "deposits@^3.1")]
#[identifiers(issue = ["sort-code-account", "iban"], require_party = ["lei"])]
mod business_account { /* ... */ }
```

And callers can use any identifier where a key is accepted:

```text
GET  /accounts/iban:GB33BUKB20201555555555             → acc_01JD3K…
POST /accounts/sort-code-account:202015-55555555/operations/withdraw
$ tkone party show passport:GB:123456789                 # entitled roles only
```

- **Keys are opaque and typed.** The engine generates them (UUIDv7, time
  ordered); each entity's key is its own type, so an `AccountId` cannot be
  passed as a `PartyId`. Their text form is prefixed for people: `acc_01JD…`,
  `pty_01JD…`. A bank's "customer number" is an identifier it issues, not
  the key: it can be reformatted, or a second brand's added, without touching
  a reference.
- **Uniqueness is claimed before the commit,** within the scheme's scope
  (`global`, `per-issuer`, `per-system`, `per-legal-entity`): a unique index on
  Postgres, an insert-if-absent on ScyllaDB. An abandoned claim expires.
- **Values are normalised before they are checked or stored:** spaces and
  case out of an IBAN, the check digits verified, so `gb33 bukb…` finds the
  same account.
- **Issued identifiers are allocated by the engine,** from ranges per scheme
  (account numbers within a sort code), with check digits, never reused where
  the scheme says so. Each engine node reserves a block of a range, so
  allocation is not a single counter every opening waits on.
- **Identifiers are effective-dated.** A new IBAN after a migration ends the
  old one; the old one still resolves, as of its time, for payments in
  flight and for statements.
- **Personal schemes follow rule 4:** encrypted per subject, found by exact
  value through a blind index, erased with the subject.
- **Imports are idempotent.** An external identifier is unique per source
  system, so loading the same file twice finds what the first load made.
- **Operations are idempotent.** A caller sends an idempotency key; the engine
  keeps `(instance, key) → result` for a window the definition sets (seven
  days by default), and a retry gets the first result.
- **Parties merge by redirect.** Duplicate customers are found late, always.

  ```text
  $ tkone party merge pty_01JB… --into pty_01JA…     # maker, then checker
  ```

  The merged party gains `merged_into`, effective from now. Nothing that
  refers to it is rewritten (facts never are): reads follow the redirect, and
  views keyed by party are projected again under the survivor. Unmerging is a
  new effective version that ends the redirect. Accounts do not merge: one is
  closed and its balance moved by a booking.

## Views: four forms, no code

A view says how it is derived, not only what it holds, and it says so in one
of four forms. The engine maintains it from the actions that change its
sources (C4); nobody writes code to keep it true.

```rust
/// Re-key: the same rows, keyed for another read.
#[view(key = party_id, cluster = account_id, consistency = "eventual",
       from = AccountPartyRole)]
struct AccountsByParty { party_id: PartyId, account_id: AccountId, role: Role }

/// Latest: the current value of effective attributes.
#[view(key = account_id, consistency = "with-instance",
       latest_of = [Account.status, Limit.overdraft])]
struct AccountStatus { account_id: AccountId, status: Status, overdraft: Money }

/// Fold: an aggregation over facts, grouped, and filtered if needed.
#[view(key = account_id, consistency = "with-instance", from = Entry,
       group_by = address, fold = sum(signed(amount)))]
struct Balances { account_id: AccountId, address: BalanceAddress, amount: Money }

#[view(key = account_id, consistency = "with-instance", from = Hold,
       filter = "released is none", fold = sum(amount))]
struct HoldsTotal { account_id: AccountId, amount: Money }

/// Compose: views of the same key, side by side; derived fields by formula.
#[view(key = account_id, consistency = "with-instance",
       compose = [AccountStatus, Balances, HoldsTotal],
       derive = { available: "Balances[Available] - HoldsTotal + AccountStatus.overdraft" })]
struct AccountState;
```

| Form | From | Gives | Example |
|---|---|---|---|
| **Re-key** | an entity, relation or view | the same rows under another key | accounts by party, bookings by scheme reference |
| **Latest** | effective attributes | their current values | status, limits, roles |
| **Fold** | facts, filtered, grouped | `sum`, `count`, `min`, `max`, `first`, `last` | balances, holds, arrears days, entries this month |
| **Compose** | views of the same key | one row with all their fields, plus formulas over them | `AccountState`: what a hook reads about its account |

- **Folds are mergeable on purpose.** Every aggregation can be computed in
  parts and combined, which is what lets [hot accounts](hot-accounts.md) sum
  sharded inboxes and the day's close write checkpoints instead of folding
  from the first entry.
- **Most "computed" state is a fold once balance types are chosen well.**
  Accrued interest is not a special view: the end-of-day hook books accruals
  to the `accrued` balance type (declared with extra precision, rule 5), and
  the balance of that type is the accrued interest.
- **Formulas in `derive` are arithmetic over the composed fields,** with the
  types of rule 5: no calls, no conditions on other instances, no I/O.
- **A view's derivation is part of the schema.** Changing a fold or a
  formula is a new view version, rebuilt from the journals, then swapped
  (rule 3).
- **Views are where `requires` and `returns` read from.** A hook's inputs
  and an operation's result are selections of views
  ([hooks](contract-hooks.md#operation-results)).

One escape hatch, later and off by default: a **projector** component, pure
and deterministic like a hook, for a view no form can express. It needs a
reason at registration; if several appear for the same reason, a form is
missing.

## All together

The core's party, with every rule that applies to it:

```rust
#[model(name = "core", version = "1.5.0")]
mod core {
    #[entity(key = party_id, subject = party_id, retain = "after(closed) + 7y")]
    #[identifiers]                                       // 9: passport, LEI, … by scheme
    struct Party {
        party_id: PartyId,                               // 9: typed, opaque
        kind: PartyKind,                                 // closed code set
        #[renamed(from = "name")]                        // 1: id kept
        #[personal] #[effective] legal_name: Name,       // 4: encrypted per subject
        #[personal(special)] date_of_birth: NaiveDate,
        #[effective] merged_into: Option<PartyId>,       // 9: merge by redirect
    }

    #[relation(Account <-> Party, max_per_party = 50, max_per_account = 20)]   // 6
    struct AccountPartyRole { #[effective] role: Role }

    #[effective(key = account_id)]
    struct Limit { account_id: AccountId, overdraft: Money }                   // 5
}
```

Rules 2, 3 and 8 need nothing in the source: they are checks `model plan`
runs and fields the engine writes. Rule 7 is a line in a definition.

## Later

Worth having; none is expensive to add once data exists:

| Idea | What it gives |
|---|---|
| **Served versions of views** | readers ask for view version 1 or 2 while one is stored; cleaner than renaming a rebuilt view |
| **Desired vs observed** | an instance's parameters (desired) named apart from its derived state (observed); implicit today |
| **Profiles** | a facet that narrows a core type (a field required for mortgages), and code sets bound as *required*, *extensible* or *preferred* |
| **Where each invariant lives** | inside one entity: the model; across one instance's entities: the engine at commit; across instances: the ledger or an asynchronous check. A rule that fits none of these is not an invariant |
| **Provenance as a guarantee** | every view value traceable to the hook, implementation, inputs and reference data that produced it; mostly present already (C3, C17) |
| **Docs and owners in the schema** | the schema doubles as the catalogue: who owns a field, why it is deprecated |
| **Generated test data** | generators from the schema, respecting bounds and code sets, for [simulation](contract-engine.md#simulation) |
| **Escrowed counters** | bounded resources (stock, credit lines shared across accounts) split into allowances per shard, rebalanced; the bounded cousin of [hot accounts](hot-accounts.md) |

## Decided, so they are not reopened by accident

- **No model extension without code in v1.** Tenants and banks extend the
  core with facets in model crates. Fields added at run time become
  entity-attribute-value tables, which every other rule here (ids, classes,
  bounds, exact types) would have to be rebuilt for.
- **Nothing is deleted.** Entities close and are archived; facts are reversed.
  The one exception is erasure, by key (rule 4).
- **The core stays small:** party, account, ledger, reference data (C15).
  Every other domain extends it. A core that grows to hold every domain's
  entities is an ORM for the whole company, and every change to it moves
  every domain.
